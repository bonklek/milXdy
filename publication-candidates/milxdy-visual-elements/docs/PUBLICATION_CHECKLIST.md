# Publication checklist

## Decisions

- [ ] Final organization and repository name are approved.
- [ ] Contributor wording clearly separates local custom freedom from
      default/upstream requirements.
- [ ] The upstream review roles and support/escalation route are named.

## Repository

- [ ] `npm run verify` passes from a clean checkout.
- [ ] Local-custom schemas accept declared, unknown, and non-VPL metadata.
- [ ] Upstream-default fixtures fail unless VPL evidence and approvals exist.
- [ ] Human pages match the machine-readable local/upstream scope.
- [ ] Every bundled repository/default file follows the repository VPL.
- [ ] No private path, private planning text, credential, or personal data is
      present.
- [ ] No page claims that local package acceptance is project endorsement.

## Guide and examples

- [ ] HTML uses native semantics and accessible names.
- [ ] Examples cover light, dim, dark, system, and forced colors.
- [ ] Keyboard, focus, Escape, live-region, 200% zoom, and 320 px checks pass.
- [ ] Package-owned motion has a reduced-motion substitution.
- [ ] Sound requires activation, mute/volume, a visible equivalent, and
      rate-limiting.
- [ ] The Music walkthrough runs as a local customization without catalog or
      VPL approval.
- [ ] The Music upstream-promotion section separately enforces VPL.

## Release

- [ ] The release commit is clean and reviewed.
- [ ] A fresh local author can declare and build a custom asset without a
      catalog server or remote runtime download.
- [ ] A default/upstream submission can be verified from hashes and review
      records.
- [ ] A normal milXdy extension build/archive contains no source-library tree.
- [ ] No repository, branch, release, or announcement is created until the
      maintainer explicitly approves publication.
