# Asset and contribution policy

This policy separates user-controlled local customization from assets that ship
as part of milXdy's default/upstream codebase.

## Local custom packages

Local custom packages are license-neutral from milXdy's point of view. Authors
choose their own assets and are responsible for satisfying any obligations that
apply to their use or distribution. VPL is recommended when an author wants the
same open remix expectations as milXdy, but it is not a local runtime or
composition requirement.

Local tooling should:

- accept `declared`, `unknown`, and `not-applicable` license metadata;
- permit any declared license identifier and required notices;
- treat source/provenance records as recommended reproducibility information;
- validate file identity, safe paths, MIME/format, dimensions/duration, and
  package declarations regardless of license;
- warn rather than block when optional license/provenance fields are absent;
- never present local acceptance as project endorsement; and
- never upload, publish, or submit a local asset without explicit user action.

The guide does not claim that noncommercial, personal, or local use eliminates
third-party obligations. It simply keeps milXdy's upstream contribution policy
out of the way of local customization.

## Default/upstream packages

Assets proposed for the milXdy codebase, official default packages, or an
official published visual bundle must be VPL. Upstream promotion requires:

1. exact local source and export files identified by SHA-256;
2. source URL or origin note, retrieval date, creator/source context, and
   acquisition method;
3. explicit VPL evidence covering the exact file;
4. the complete project VPL text and required notices;
5. no additional restriction or non-VPL dependency in the promoted work;
6. parent IDs/hashes and material transformations for derivatives;
7. alt/decorative guidance, theme/background assumptions, and rendered-size
   checks;
8. safe packaging with no runtime hotlink or undeclared binary;
9. technical, visual/cultural, accessibility, license, and release approval;
   and
10. an immutable `UPSTREAM_APPROVED` decision tied to final hashes.

This is an operational project policy, not legal advice.

## Manifest scopes

- `local-custom`: author-controlled material used by a local package. License
  metadata may be declared, unknown, or not applicable.
- `upstream-default`: material proposed for default distribution by milXdy.
  VPL evidence and full review are mandatory.

Changing `distributionScope` from `local-custom` to `upstream-default` is a
promotion request. It does not happen automatically because a package works
well locally or because an asset was generated by AI.

## Entry roles

- `source-asset`: an original or imported source used for local customization
  or an upstream derivative.
- `derived-asset`: a modified, generated, composited, recolored, or transformed
  output linked to its parent records.
- `ui-primitive`: an icon, frame, divider, texture, token, or similar reusable
  implementation element.

## Local workflow

1. Choose or create an asset.
2. Keep the original separate from exports.
3. Record a stable local ID and hashes when reproducibility matters.
4. Declare only shipped exports in `milxdy.app.json`.
5. Add actual license/notices when known or mark status `unknown`.
6. Test visual, responsive, accessibility, motion, and sound behavior.
7. Build locally; no catalog admission is required.

## Upstream promotion workflow

1. Start from the exact local manifest and bytes.
2. Confirm the source and every required dependency are VPL.
3. Complete missing provenance and VPL evidence fields.
4. Set `distributionScope` to `upstream-default`.
5. Run strict validation and all five review lanes.
6. Record `UPSTREAM_APPROVED` against final hashes.
7. Add the version to the official/default index.

If VPL evidence is unavailable, the asset remains usable locally but is not
eligible for default/upstream inclusion. That is a distribution decision, not a
failure of the local package.

## AI-assisted work

AI may help transform local assets without catalog approval. Authors should
record the exact input and material changes when they want repeatability. AI
output does not establish ownership or licensing and cannot approve upstream
promotion.

For upstream promotion, retain the parent graph, tool/model disclosure where
available, publication-safe edit notes, VPL continuity, and human reviews.

## Technical safety

Both lanes reject technically unsafe package content. Validate file signatures,
dimensions/duration, decompression limits, metadata policy, safe relative paths,
and declared hashes. SVG used by a package must not contain scripts, event
handlers, external references, `foreignObject`, or active content.

Safety checks protect the local build; they do not decide an asset's license.

## Deprecation, replacement, and removal

Local authors may replace their own files and update their manifests. Published
upstream hashes remain immutable: replacement receives a new version, and a
removal advisory keeps the affected ID/version/hash and migration guidance
visible.
